## 0. 你们的条件摘要（方案就是从这里推出来的）

| 维度 | 实际情况 | 对方案的影响 |
|---|---|---|
| **项目性质** | 课题组**横向项目的子板块**，用于检验水平 | 交付物要"拿得出手"：可复现仓库 + 技术报告 + 能演示的网站 + **主动汇报** |
| **验收节点** | 学长说"有一定进展之后再找他汇报"（**没有硬节点**） | ⚠️ **必须自设节点**——没有 deadline 的项目最容易烂尾。本方案设 W2、W4 两个主动汇报点 |
| **时间预算** | 5~8 周，**两人合计每周 10h** | 取 **6 周 × 10h = 60 人时**。这是**两个人的总时间**，所以必须大幅砍需求（见 §2） |
| **A 的机器** | RTX 5060 Laptop 8 GB（**B 档**） | 能跑 A 轨生成（SD1.5 路线）+ 全部训练；跑不了 SDXL 路线 |
| **B 的机器** | Windows 笔记本，**无独显**（C 档） | 承担数据 / 评测 / 筛选 / 网站 / 文档；**两台都是 Windows，省掉一堆跨平台麻烦** |
| **网络** | 境外站点**基本都不稳定** | 🔴 **最大风险**。全程走镜像（[`MIRRORS.md`](MIRRORS.md)），且 **B 轨必须优先选 Zenodo 上的数据集** |
| **技能** | 两人都没碰过深度学习；**数学基础都较好**；A 代码/算法强但 **Python 写得少** | 学习**必须嵌进任务**（不单独占工时）；A 前两周刻意练 Python"三件套"（见 §6.2） |
| **协作方式** | Git + 各自下载，不互传大文件 | 谁生成谁训练；manifest 入库、图片不入库 |
| **取向** | 平衡：保交付 + 尽力做个亮点 | 先保 MVP 闭环，再用剩余时间加"身份保持生成"这个亮点 |

**一句话总结你们的处境**：时间是最大的约束（60 人时），网络是最大的风险；**A 手上唯一能出技术亮点的是那台 8 GB 的 GPU，而 B 手上握着整个项目的"尺子"（评测器）和"门面"（网站与报告）**——两半缺一不可。

## 1. 目标定义：6 周后你们要能拿出什么

### 1.1 四件交付物（缺一不可）

| # | 交付物 | 判断标准 | 主要负责人 |
|---|---|---|---|
| 1 | **可复现的仓库** | 别人按 README 能跑出和你们一样的数字；两台机器都能跑 | A（B 复核） |
| 2 | **技术报告**（6~10 页） | 含：问题、方法、实验设置、结果表、结论、**局限**、复现指南 | A 主笔，B 排版与文献 |
| 3 | **展示网站**（静态，5 个页面） | 打开就能看懂：方法图 + 真/合成对比图库 + 指标图表 + 结论 | B |

### 1.2 本项目的三个可交付问题（**这是全项目的重心**）

原来的 5 个研究问题在 60 人时里答不完，砍成 3 个：

| ID | 问题 | 靠什么实验回答 | 亮点 | 谁主导 |
|---|---|---|---|---|
| **Q-A** | **现成的合成人脸数据**加进训练集，识别性能会变好吗？加多少合适？ | E4b（B 轨）+ 比例扫描 3 点 | 直接回答"合成数据有没有用" | B 备数据，A 跑实验 |
| **Q-B** | **给同一个人生成更多照片（身份保持生成）**，比传统增强更有效吗？ | E4a（A 轨）vs E2（传统增强，**图片总数对齐**） | ⭐ **这是你们区别于"调包跑 demo"的核心**：它把"数量"和"多样性"分开了 | A |
| **Q-C** | 代价是什么？ | 质量/姿态分桶表现 + 许可与可检测性的**文献讨论** | 体现你们有工程伦理意识（学长会看这个） | B |

### 1.3 ⚠️ 一条必须讲清楚的方法学细节（**这条会让你们显得很专业**）

B 轨和 A 轨回答的是**两个不同的问题**，绝不能混在一条曲线里：

| 轨道 | 加进去的是什么 | 学名叫法 | 回答 |
|---|---|---|---|
| **B 轨**（下载的 DigiFace-1M / Digi2Real 等） | **新的、合成出来的"人"** | 增加**类别数**（new identities） | 合成身份能否补充**类别多样性**？ |
| **A 轨**（本地对真实身份生成） | **已有那批人的更多照片** | 增加**类内样本数**（more samples per identity） | 同身份的更多变化能否提升**类内泛化**？ |

**报告里必须分两节写**，并各自定义清楚"比例"是什么：
- B 轨比例 = 合成**身份数** / 总身份数（类别层面）
- A 轨比例 = 合成**图片数** / 总图片数（样本层面，身份数不变）

> 把这两个混在一起是这类项目最常见的错误。你们只要在报告里明确区分，就已经超过大多数同水平的工作了。

## 5. 汇报包（"有进展"到底长什么样）

学长说"有一定进展再找他"，所以**你们要自己定义"进展"**。建议这样汇报两次：

**汇报点 1（W2 末）——主题："流水线通了"**
- 一张图：对齐抽样网格（证明数据管线是对的）
- 一张表：E0 / E1 指标 vs 公开报道数字（证明评测可信）
- 一句话：下周做什么、风险是什么

**汇报点 2（W4 末）——主题："有结论了，能演示了"**
- 一张图：**同一身份的真实图 vs 生成图**（这是最抓眼球的）
- 一张表：E1 / E2 / E4a / E4b 四组数字 + 误差
- 一个能当场打开的网站
- 一段诚实的话：哪些成立了、哪些没成立、为什么

**汇报时主动说清楚的三件事**（会让你们显得很专业）：
1. 我们**分开**测了"增加合成身份"和"给同一身份增加照片"——它们是两个问题；
2. 我们**对齐了图片总数**才敢说"多样性比数量更有效"；
3. 我们记录了**所有没成功的尝试**，并写进了局限。

## 6. 学习方案（针对"零 DL 经验 + 数学好 + A 的 Python 少"）

### 6.1 原则：**不单独安排学习周，全部嵌进任务**

每周只花 **30~60 分钟**做"定向阅读"，其余靠动手。`LEARNING.md` 的六阶段按下面的方式压缩：

| 阶段 | 怎么做 | 时间 | 主责 |
|---|---|---|---|
| **L0** 直觉 | 必做（W1，手算余弦 + 相似度矩阵） | 各 0.5h | A+B |
| **L1** 识别基础 | **必做**；因为数学好，可以深入看 ArcFace 的角度间隔公式 | 1h | **B 主责**（评测协议） |
| **L2** 生成基础 | **压缩为"用中学"**：只读"四种条件注入方式"那张表 + 跑通 4 张生成图 | W4 实操中顺带 | A |
| **L3** 身份保持 | **压缩**：只抓"保真 vs 多样性"的取舍，其余在实操中理解 | 1h | A 主责，B 听懂即可 |
| **L4** 实验方法 | **必做**：手算 TAR@FAR + 用标准差判断显著性（数学优势在这里发挥） | 1h | **B 主责**，A 复核结论措辞 |
| **L5** 伦理许可 | 半小时：只做"数据许可核对表" | W5 顺带 | B |
| **L6** 论文 | **只读 5 篇**（不是 15 篇）：ArcFace、SynFace、DigiFace-1M、Arc2Face、Huber et al. | 每周各 20 分钟，共 ~1.5h | 一人一半，互相讲 |

### 6.2 A 的 Python 短板：前两周刻意练「三件套」

A 算法强但 Python 少，**不要试图通读 Python 教程**。只练这三样，它们覆盖了本项目 90% 的代码：

1. **`argparse`**：每个脚本都有 `--config / --dry-run` 入口（照抄自己写的第一个脚本即可）
2. **`pathlib`**：所有路径用 `Path` 拼接，**禁止手写字符串路径**（这是两人两机不打架的前提）
3. **`pytest`**：每个核心函数配一个"用假数据验证真逻辑"的测试（例如用 3 个已知向量验证余弦相似度）

> 这三样练熟，A 的 Python 就够用了；剩下的时间应该花在实验设计和结果解释上——**那才是 A 的优势区**。
> B 也会写 Python（评测器、筛选、网站数据导出），同样用这三件套，只是紧迫度低一些——**评测器里最需要 `pytest`**。

### 6.3 B 的学习重点（差异化）

B 同样零基础，但**不需要碰训练与生成**，所以：

- 优先学 **L1 的评测协议** 与 **L4 的统计**（逻辑清晰、数学味足、不依赖 GPU）——**这两块恰好是 B 的主责，学完立刻能用**；
- 用"网站"作为正反馈来源：每做完一个图表就能看到页面变化；
- 不需要深入扩散模型（L2/L3 只求"能听懂 A 讲"）。

## 8. 汇报时可能被问到的 8 个问题（提前想好答案）

1. **"你们的数据量这么小，结论可信吗？"** → 承认规模限制；强调我们比的是**内部相对差异**、且关键对比做了 3 seed；绝对值不与论文比。
2. **"为什么不直接在 MS1M 上训练？"** → 消费级显存与时间不允许；我们的贡献是**低成本配方**（RQ5）与方法学对照。
3. **"合成数据到底有没有用？"** → 分两轨回答：增加合成**身份** vs 增加同身份**照片**，这是两个问题，结论可能不同。
4. **"你们怎么知道提升不是来自图片变多？"** → 因为我们做了 E2 传统增强对照，**并严格对齐了图片总数**。
5. **"生成的脸和真人像不像？"** → 有量化（身份相似度分布）+ 人工抽检通过率 + 图库展示，包括**不够像的样本**。
6. **"合成数据有隐私问题吗？"** → 有：文献证明合成数据集可能被成员推断攻击检索出真实样本；我们记录了来源与生成参数，并做了可检测性讨论。
7. **"这东西能落地吗？"** → 谈成本收益：A 轨的成本（显存/时间）vs 收益；明确说本项目的规模**不能**外推到工业场景。
8. **"如果重做一次，你们会改什么？"** → 提前准备 2 条（例如"先做 B 轨再碰 A 轨""评测器必须早于训练管线"）——这题答好非常加分。

> 分工建议：**1/2/8 由 A 主答**（技术判断），**3/4/5 由 B 主答**（数据与评测），**6/7 两人都能答**。提前对一遍口径，避免当场互相矛盾。
